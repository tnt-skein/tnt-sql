# Построитель запросов

`tnt-sql` собирает SQL вызовами, а не склейкой строк, и **ничего
не выполняет**: `build` отдаёт пару «текст и параметры», а в базу ходит
драйвер. Диалекты — PostgreSQL, MySQL и SQL самого Tarantool
(`box.execute`).

```lua
local sql = require('tnt.sql')

local users = sql.table('users', { 'id', 'name', 'email', 'votes' })   -- белый список столбцов
local text, params = users:select('id', 'name'):where('votes', '>', 100):build('postgres')
--> 'select "id", "name" from "users" where "votes" > $1::int8', { n = 1, 100 }
```

Зависимости: [`tnt-must`](https://github.com/tnt-skein/tnt-must)
(проверки аргументов и тексты отказов),
[`tnt-collection`](https://github.com/tnt-skein/tnt-collection) (столбцы
строки по порядку имён) и
[`tnt-storage`](https://github.com/tnt-skein/tnt-storage) (кодирование
значений параметров и отказ `TntStorageFailure`). Настроек и состояния
у пакета нет.

## Зачем пакет

Запрос, склеенный из строк, — это место, где значение становится
текстом, а имя из адресной строки — именем столбца. Пакет закрывает это
тремя вещами:

- **Значение — всегда параметр.** Оно никогда не склеивается с текстом,
  и внедрению SQL взяться неоткуда. Кодирует его `tnt-storage`
  (`value.wire`) тем же правилом, что и драйвер: `int64`, `decimal`,
  `uuid`, время, JSON и байты доезжают до сервера без потерь.
- **Имя — только из белого списка.** Всякий запрос начинается
  с объявления таблицы, и столбец, которого в нём нет, в текст
  не попадёт, откуда бы ни пришло имя.
- **Один построитель на три диалекта.** Знак параметра, кавычка имени,
  `returning`, `upsert` и `seqscan` у PostgreSQL, MySQL и SQL Tarantool
  свои. Запрос собирается один раз и под любой из них, а белый список
  сторожится в одном месте, а не в каждом драйвере.

Готового в Tarantool нет: встроенный SQL (`box.execute`) текст принимает,
но не собирает, а среди официальных роков построителя нет. Своё здесь —
только сборка; то, что уже решено, взято из зависимостей: значения
кодирует `tnt-storage`, столбцы строки упорядочивает `tnt-collection`
(`keys`), тексты отказов собирает `tnt-must`. И раз пакет ничего
не выполняет, он проверяется целиком без базы и без докера.

Три слоя, и у каждого своя забота:

| Слой | Что делает |
|---|---|
| разбор адресной строки | разбирает `?filter[…]`, `?sort=`, `?page[…]` по белому списку формы |
| `tnt-sql` | собирает текст с параметрами по белому списку таблицы |
| драйвер | выполняет |

Слить любые два — открыть дорогу значению из адресной строки прямо
в запрос. Поэтому условия разбора приходят сюда данными (`filter`,
`sort`, `page`), и имя поля ещё раз проходит белый список таблицы: разбор
адреса и сборка запроса сторожат каждый своё.

## Как пользоваться

```lua
local sql = require('tnt.sql')

-- белый список: таблица и её столбцы, один раз на приложение
local users = sql.table('users', { 'id', 'name', 'email', 'votes' })

local query = users:select('id', 'name'):where('votes', '>', 100):order_by('name', 'desc'):limit(10)

query:build('postgres')
--> select "id", "name" from "users" where "votes" > $1::int8 order by "name" desc limit 10
--> { n = 1, 100 }
query:build('mysql')
--> select `id`, `name` from `users` where `votes` > ? order by `name` desc limit 10
--> { n = 1, 100 }
query:build('tarantool')
--> select "id", "name" from "users" where "votes" > ? order by "name" desc limit 10
--> { n = 1, 100 }
```

Пара уходит драйверу как есть: `params` — массив с полем `n`, и `nil`
посреди значений не теряется. Для `box.execute` — тоже как есть:
`box.execute(text, params)`.

Запрос — изменяемый объект: каждый вызов дописывает его и отдаёт его же.
Собирать его можно сколько угодно раз и под любой диалект.
Диалект — имя либо таблица диалекта драйвера с полем `name`
(`build(driver.dialect)`): из таблицы берётся только имя, знак параметра
и кавычку пакет знает сам.

| Вызов | Что делает |
|---|---|
| `sql.table(name, columns)` | объявление таблицы — белый список столбцов |
| `T:as(alias)` | та же таблица под псевдонимом — для выборки |
| `T:select(...)` | выборка; без столбцов — все объявленные |
| `T:insert(rows)` | вставка строки либо списка строк |
| `T:upsert(rows, unique_by, update)` | вставка с обновлением на конфликте |
| `T:update(values)` | правка |
| `T:delete()` | удаление |
| `sql.raw(text, ...)` | текст руками со знаками `?` — целый запрос либо кусок другого |
| `sql.column(name)` | столбец там, где ждут значение |
| `sql.OPERATORS` | операторы условий по порядку |
| `sql.POSTGRES`, `sql.MYSQL`, `sql.TARANTOOL` | имена диалектов |

Диалекты различаются так:

| | `postgres` | `mysql` | `tarantool` |
|---|---|---|---|
| параметр | `$1`, `$2`… | `?` | `?` |
| имя | `"имя"` | `` `имя` `` | `"имя"` |
| `returning` | есть | нет | нет |
| `upsert` | `on conflict … do update` | `on duplicate key update` | нет |
| полный просмотр | сам | сам | только с `seqscan` у каждой таблицы |

### Белый список

Всякий запрос начинается с объявления таблицы, и столбец, которого в нём
нет, в текст не попадёт — ни в выборку, ни в условие, ни в порядок,
ни в `insert`, откуда бы ни пришло имя. Без этого фильтр из адресной
строки становится способом прочитать чужое:
`filter[password_hash][prefix]=a` отвечает числом найденных строк,
и хеш подбирается по знаку.

```lua
local query = users:select('id'):filter({ { field = 'password_hash', op = 'prefix', value = 'a' } })

query:build('postgres')
--> исключение: where: столбца «password_hash» нет в белом списке users (id, name, email, votes)
```

Имя проверяется дважды. Форма — в миг вызова, на строке вызывающего:
латиница, цифры и `_`, не с цифры, не длиннее 63 байтов (длиннее
PostgreSQL обрезает имя молча, и два длинных имени с общим началом стали
бы одним). Такое имя в кавычках диалекта не закроет кавычку и не начнёт
второй оператор, чем бы ни было. Белый список — при сборке, когда
известны все таблицы запроса.

```lua
users:select('id'):where('name; drop table users', '=', 1)
--> исключение: where: столбец — имя из латиницы, цифр и _, не с цифры и не длиннее 63 байтов, а не «name; drop table users»
```

Имена всегда в кавычках: SQL Tarantool без кавычек поднимает имя в верхний
регистр (`users` ищет спейс `USERS`), а PostgreSQL — опускает в нижний.
Имя в кавычках значит ровно то, что объявлено.

Столбец без таблицы ищется у всех таблиц запроса: объявленный у одной —
её, у двух — неоднозначность и исключение, у ни одной — исключение.
С таблицей (`posts.title`, `u.id`) — только у неё; таблица — имя либо
псевдоним.

### Выборка

```lua
local posts = sql.table('posts', { 'id', 'user_id', 'title' })

users:select('users.id', 'title', 'posts.id as post_id')
    :left_join(posts, 'posts.user_id', '=', 'users.id')
    :where('title', 'prefix', 'p')
    :build('mysql')
--> select `users`.`id`, `title`, `posts`.`id` as `post_id` from `users` left join `posts` on `posts`.`user_id` = `users`.`id` where `title` like ? escape '!'
--> { n = 1, 'p%' }
```

| Вызов | Что делает |
|---|---|
| `select(...)` | столбцы: `'имя'`, `'таблица.имя'`, `'… as псевдоним'`, `sql.raw(…)` |
| `distinct()` | `select distinct` |
| `join(T, first, op, second)` | `inner join … on first op second`; `op` — `=`, `<>`, `<`, `<=`, `>`, `>=` |
| `left_join(T, first, op, second)` | `left join` тем же видом |
| `where(...)`, `or_where(...)`, `filter(conditions)` | условия, раздел ниже |
| `group_by(...)` | столбцы либо `sql.raw` |
| `having(...)` | условие на группы тем же видом, что `where` |
| `order_by(column, direction)` | `asc` (по умолчанию) либо `desc`; столбец, псевдоним выборки либо `sql.raw` |
| `sort(list)` | порядок, разобранный из адресной строки |
| `limit(n)`, `offset(n)` | целые от 0 до 2^53 |
| `page(page)` | страница, разобранная из адресной строки |
| `seqscan()` | SQL Tarantool: разрешить просмотр таблицы целиком |
| `build(dialect)` | текст и параметры |

**Без столбцов выборка берёт объявленные, а не `*`.** Белый список
сторожит и чтение: то, что лежит в таблице сверх объявления, наружу
не уходит. С соединением объявленные столбцы первой таблицы пишутся
с её именем:

```lua
users:select():join(posts, 'posts.user_id', '=', 'users.id'):build('postgres')
--> select "users"."id", "users"."name", "users"."email", "users"."votes" from "users" inner join "posts" on "posts"."user_id" = "users"."id"
--> { n = 0 }
```

**Имена в выборке уникальны.** Рок отдаёт строку словарём по именам
столбцов и повтор имён схлопывает в последнее значение молча, поэтому
второй `id` без псевдонима — исключение, а не потерянный столбец:

```lua
users:select('users.id', 'posts.id')
--> исключение: select: имя «id» в выборке дважды, и рок оставит одно — дайте псевдоним: posts.id as другое
```

Таблицу к самой себе присоединяют под псевдонимом: `users:as('boss')`.
Таблица, которая уже есть в запросе, второй раз без псевдонима —
исключение.

**Порядок** принимает псевдоним выборки — так его понимают все три
сервера, — а условие нет: `where` по псевдониму PostgreSQL не примет.
Направление пишется всегда, и `asc` тоже.

```lua
users:select('votes', sql.raw('count(*) as total'))
    :group_by('votes')
    :having(sql.raw('count(*)'), '>=', 2)
    :order_by(sql.raw('total'), 'desc')
    :build('postgres')
--> select "votes", count(*) as total from "users" group by "votes" having count(*) >= $1::int8 order by total desc
--> { n = 1, 2 }
```

**`limit` и `offset` — числа в тексте, а не параметры.** Это проверенные
целые, а не данные: `pg` передаёт число типом `numeric`, и `limit $1`
с `numeric` сервер не принимает. `offset` без `limit` — исключение
сборки: MySQL и Tarantool так не умеют (проверено запуском).

**`seqscan()` — только для SQL Tarantool.** С 3.0 он отказывает
«Scanning is not allowed for 'users'» выборке, которой не хватает
индекса, пока её не разрешили словом `seqscan` у каждой таблицы — у
присоединённой тоже. Слово разрешает просмотр, а не велит его: индекс
берётся, где он есть. Прочие диалекты слова не пишут, правке и удалению
оно не нужно (у них `seqscan` — синтаксическая ошибка).

```lua
users:select('name', 'title'):join(posts, 'posts.user_id', '=', 'users.id'):seqscan():build('tarantool')
--> select "name", "title" from seqscan "users" inner join seqscan "posts" on "posts"."user_id" = "users"."id"
--> { n = 0 }
```

### Условия

```lua
users:select('id')
    :where('votes', '>', 1)
    :where(function(group)
        group:where('name', '=', 'a'):or_where('email', 'is null')
    end)
    :where('id', 'in', { 1, 2 })
    :build('postgres')
--> select "id" from "users" where "votes" > $1::int8 and ("name" = $2 or "email" is null) and "id" in ($3::int8, $4::int8)
--> { n = 4, 1, 'a', 1, 2 }
```

| Оператор | Справа | Текст |
|---|---|---|
| `=`, `<>`, `<`, `<=`, `>`, `>=` | значение | `x > $1` |
| `like`, `not like` | образец как есть | `x like $1` |
| `in`, `not in` | список; пустой — ложь и истина | `x in ($1, $2)`, `1 = 0`, `1 = 1` |
| `between`, `not between` | пара | `x between $1 and $2` |
| `prefix`, `contains` | кусок строки буквально | `x like $1 escape '!'` |
| `is null`, `is not null` | ничего | `x is null` |

- **Оператор — только из перечня.** Он единственное слово условия, которое
  попадает в текст как есть, и незнакомый оператор — исключение, откуда
  бы он ни пришёл. Короткой записи `where('name', 'John')` нет: второй
  аргумент — всегда оператор. Четвёртого аргумента со связкой («и» или «или»
  последним аргументом) тоже нет — «или» пишут `or_where`, а лишний аргумент —
  исключение, а не молча потерянное «или».
- **Функция — скобки.** Условия, которые она поставит группе, идут вместе;
  так пишется «или» внутри «и». Группа без условий не пишется вовсе.
  Без скобок «и» связывает крепче «или»: `where(a):where(b):or_where(c)` —
  это `a and b or c`, то есть `(a and b) or c`, как и в самом SQL.
- **Сравнения с NULL нет.** `x = NULL` не бывает истинным, поэтому `nil`
  и `box.NULL` в сравнении и в списке — исключение, а не молчаливое
  `is null`: иначе фильтр, чьё значение не пришло, превращался бы
  в поиск пустоты. Для пустоты — `is null`.
- **`prefix` и `contains` — кусок буквально.** `%`, `_` и знак
  экранирования `!` в нём экранируются, и уходит он параметром. Знак
  экранирования — `!`, а не обратная черта: её MySQL читает экранированием
  уже в литерале, и `escape '\'` у него — незакрытая строка.
- **Справа — столбец либо текст руками.** `sql.column('created_at')` —
  имя по белому списку, `sql.raw('now() - ?::interval', '1 day')` — текст
  со своими значениями. Текст руками годится и целым условием, и левой
  частью: `where(sql.raw('length(?)', sql.column('name')), '>', 3)`.

```lua
users:select('id'):where('name', 'contains', '50%'):build('mysql')
--> select `id` from `users` where `name` like ? escape '!'
--> { n = 1, '%50!%%' }

users:select('id'):where('email', '=', nil)
--> исключение: where: сравнение с NULL не бывает истинным — пишите «is null» либо «is not null»
```

#### Условия, порядок и страница из адресной строки

Разбор адресной строки (`?filter[votes][gte]=10&sort=-votes,id&page[size]=50&page[number]=2`)
отдаёт условия, порядок и страницу данными — сюда они идут как есть:

```lua
local asked = {
    filter = {
        { field = 'votes', op = 'gte', value = 10 },
        { field = 'name', op = 'prefix', value = 'st' },
        { field = 'id', op = 'in', value = { 5, 6 } },
    },
    sort = { { field = 'votes', direction = 'desc' }, { field = 'id', direction = 'asc' } },
    page = { size = 50, number = 2, offset = 50 },
}

users:select('id', 'name'):filter(asked.filter):sort(asked.sort):page(asked.page):build('postgres')
--> select "id", "name" from "users" where "votes" >= $1::int8 and "name" like $2 escape '!' and "id" in ($3::int8, $4::int8) order by "votes" desc, "id" asc limit 50 offset 50
--> { n = 4, 10, 'st%', 5, 6 }
```

| Вызов | Что принимает |
|---|---|
| `filter(conditions)` | список `{ field, op, value }`, все через «и» |
| `sort(list)` | список `{ field, direction }`, `direction` — `asc` либо `desc` |
| `page(page)` | `{ size, offset }`: `size` — `limit`, `offset` — `offset`; с `after` — исключение |

Операторы разбора идут словами и переводятся так: `eq` — `=`, `ne` —
`<>`, `gt`, `gte`, `lt`, `lte` — `>`, `>=`, `<`, `<=`, `in` — `in`,
`prefix` и `contains` — кусок буквально. В текст попадает только знак
из этого перевода, а не слово из адреса. Имя поля — имя Lua у формы
[`tnt-data`](https://github.com/tnt-skein/tnt-data), и у таблицы столбец
должен зваться так же.

Страница номером — `limit` и `offset`. Страница курсором (`page.after`) —
исключение: курсор — строка приложения, продолжение по ключу ставит
`where`, и молча отданная первая страница вместо следующей хуже отказа.
Приложение, разобрав курсор, отдаёт `{ size = page.size }`.

### Вставка, правка, удаление

```lua
users:insert({ { id = 1, name = 'a' }, { id = 2, name = box.NULL } }):build('tarantool')
--> insert into "users" ("id", "name") values (?, ?), (?, ?)
--> { n = 4, 1, 'a', 2, box.NULL }

users:update({ votes = sql.raw('? + 1', sql.column('votes')), name = 'z' }):where('id', '=', 7):build('postgres')
--> update "users" set "name" = $1, "votes" = "votes" + 1 where "id" = $2::int8
--> { n = 2, 'z', 7 }

users:delete():where('votes', '<', 1):build('mysql')
--> delete from `users` where `votes` < ?
--> { n = 1, 1 }
```

- Строка — таблица «столбец → значение», строк — одна либо список;
  у всех строк списка столбцы одни и те же. **Столбцы идут по порядку
  имён**, а не как их написали: одинаковые строки дают один и тот же
  текст, и подготовленный запрос у сервера переиспользуется.
- **NULL в строке и в правке — `box.NULL`**: `nil` таблица не хранит,
  и столбец пропал бы молча. `box.NULL` же уходит параметром — `box.execute`
  теряет всё после дыры в массиве параметров, а `box.NULL` дыры не делает.
- **`update` и `delete` без условия — исключение.** Так чаще всего выходит
  нечаянно: фильтр из адреса оказался пуст (`filter({})` условий
  не ставит). Всю таблицу меняют, сказав это: `everything()`.

```lua
users:delete():filter({}):build('postgres')
--> исключение: delete без where меняет всю таблицу — если так и задумано, скажите everything()

users:delete():everything():build('postgres')
--> delete from "users"
--> { n = 0 }
```

#### `upsert`

`upsert(rows, unique_by, update)` на конфликте по `unique_by` обновляет
столбцы `update` — по умолчанию все вставленные, кроме `unique_by`.
Столбцы остальные не трогаются: проверено на PostgreSQL 16 и MySQL 8.4.

```lua
local query = users:upsert({ id = 1, name = 'a', votes = 3 }, { 'id' })

query:build('postgres')
--> insert into "users" ("id", "name", "votes") values ($1::int8, $2, $3::int8) on conflict ("id") do update set "name" = "excluded"."name", "votes" = "excluded"."votes"
--> { n = 3, 1, 'a', 3 }
query:build('mysql')
--> insert into `users` (`id`, `name`, `votes`) values (?, ?, ?) as `excluded` on duplicate key update `name` = `excluded`.`name`, `votes` = `excluded`.`votes`
--> { n = 3, 1, 'a', 3 }
query:build('tarantool')
--> исключение: upsert: в SQL tarantool нет on conflict, а insert or replace стёр бы столбцы, которых нет в строке
```

У MySQL — псевдоним строки (8.0.19 и новее; `values(x)` устарел),
а `unique_by` он не пишет: конфликт находит по любому уникальному ключу.
Пакет `unique_by` требует всё равно — у PostgreSQL без него `upsert`
не собрать. SQL Tarantool `on conflict` не знает; `insert or replace`
не то же самое — он стирает столбцы, которых нет в строке. Для спейса
есть `box.space.x:upsert`.

#### `returning`

`returning(...)` у вставки, правки и удаления — только у PostgreSQL:
рок `pg` числа затронутых строк не отдаёт, и затронутое узнают
по строкам `returning`. У MySQL и Tarantool — исключение сборки.

```lua
users:insert({ name = 'a' }):returning('id'):build('postgres')
--> insert into "users" ("name") values ($1) returning "id"
--> { n = 1, 'a' }
```

### Значения

Значение уходит параметром таким, каким его передаст рок: кодирует
`tnt-storage` (`value.wire`) — то же правило, что у драйвера.
У PostgreSQL в текст ставится приведение `$n::тип`, которое называет
`value.wire`, двум родам значений:

- **значениям не числом и не логикой** — их рок шлёт типом `text`,
  и без приведения сервер отказывает «expression is of type text»;
- **целым — `$n::int8`**: число рок шлёт типом `numeric`, и сравнение
  целого столбца с `numeric` идёт мимо индекса — `where "id" = $1`
  просматривает всю таблицу. Сравнение `int2`, `int4` и `int8` с `int8`
  индекс берёт; `numeric` и `double precision` берут его и так.
  Дробное число уходит без приведения — `numeric`.

```lua
local storage = require('tnt.storage')

users:insert({ id = 9007199254740993LL, name = storage.json({ a = 1 }) }):build('postgres')
--> insert into "users" ("id", "name") values ($1::int8, $2::jsonb)
--> { n = 2, '9007199254740993', '{"a":1}' }
```

**Отказ данных — пара.** Строка с нулевым байтом у PostgreSQL — `nil, err`
рода `rejected` (`sent = false`): рок обрезал бы её молча. Это единственный
отказ, который `build` отдаёт парой: значение пришло снаружи, и так бывает.
Значение, которое передать нельзя вовсе, — таблица без обёртки
`storage.json`, целое за 2⁵³, — исключение на строке `build`.

```lua
users:select('id'):where('name', '=', 'a\0b'):build('postgres')
--> nil, строка с нулевым байтом: pg обрезал бы её молча    (kind = rejected, sent = false)
```

### Текст руками

`sql.raw(text, ...)` — текст со знаками `?` и значениями по порядку знаков.
Знак — `?` на любом диалекте, а `build` ставит знак диалекта и приведение.
Текст годится целым запросом и куском другого — столбцом, условием,
значением, порядком, группой.

```lua
sql.raw('select ? as a, ? as b', 1, nil):build('postgres')
--> select $1::int8 as a, $2 as b
--> { n = 2, 1, box.NULL }
```

Разбор текста проверяет то, чего не проверяют ни драйвер, ни рок:

- **число знаков равно числу значений**: у `pg` лишнее значение молча
  пропадает, у `mysql` недостающее берётся со стека рока;
- **один оператор на вызов**: `;` вне кавычек — исключение, `mysql` теряет
  отказ второго оператора и фиксирует первый.

Знак внутри `'…'`, `"…"`, `` `…` ``, `-- …` и `/* … */` знаком
не считается. `??` — сам знак вопроса: одиночный `?` занят под параметр,
а так пишется оператор `?` у `jsonb` PostgreSQL. Кавычка в литерале
удваивается (`'it''s'`), обратную черту разбор экранированием не считает.

```lua
sql.raw("select 'it''s ?', ? -- ?", 1):build('postgres')
--> select 'it''s ?', $1::int8 -- ?
--> { n = 1, 1 }

sql.raw('select ?, ?', 1)
--> исключение: sql.raw: знаков ? в тексте 2, а значений 1

sql.raw('select 1; select 2')
--> исключение: sql.raw: один оператор на вызов, а в тексте «;» вне кавычек
```

**Имена в тексте руками пишет тот, кто пишет текст**, и в кавычках своего
диалекта: `"votes"` у MySQL — строка. Переносимо — через `sql.column`:
`sql.raw('? + 1', sql.column('votes'))` даёт `"votes" + 1` и `` `votes` + 1 ``.
Самостоятельный текст руками таблиц не знает, и `sql.column` в нём —
исключение сборки.

### Отказ и исключение

| Что | Как |
|---|---|
| строка с нулевым байтом у PostgreSQL | `build` → `nil, err` (`TntStorageFailure`, `rejected`) |
| негодное имя, оператор, направление, `limit`, пустая вставка, `NULL` в сравнении, число знаков у `sql.raw` | исключение на строке вызова |
| столбец не из белого списка, неоднозначный столбец, незнакомый диалект, `offset` без `limit`, `update`/`delete` без условия, `returning` и `upsert` не у своего диалекта, значение, которое не передать | исключение на строке `build` |

Отказ сборки бросается на строке того, кто позвал `build`, а не внутри
пакета: чинить надо строку, где запрос собрали. Хвостовой вызов
(`return query:build(d)`) свой кадр теряет, и место уходит на строку выше —
ловушка та же, что у проверок
[`tnt-must`](https://github.com/tnt-skein/tnt-must).

### Опасные места

- **Текст руками — это текст.** Значение, склеенное в строку `sql.raw`
  до вызова (`sql.raw('x = ' .. id)`), параметром уже не станет. Значения
  идут только аргументами после текста.
- **`where(a):or_where(b)` без скобок.** «Или» верхнего уровня делит
  всё условие: `a and b or c` — это `(a and b) or c`. Нужна группа —
  `where(function(g) … end)`.
- **Хвостовой вызов `build`** уводит место отказа на строку выше.
- **`seqscan()` на большой таблице** — просмотр целиком. Tarantool
  отказывает без него нарочно: выборке без индекса лучше найти индекс.

## Чем пришлось поступиться

- **Только объявленные таблицы.** Запроса к таблице, которой нет
  в объявлении, не собрать; подзапросов, `union`, `with` и оконных
  функций построитель не знает — это текст руками.
- **Соединение — одно сравнение двух столбцов.** Условие соединения
  из нескольких частей пишется `where` (у `left join` это меняет смысл)
  либо текстом руками.
- **Имена — латиница.** Кириллица, пробелы и точки в именах столбцов
  и таблиц не проходят проверку формы; схема (`public.users`) — тоже.
- **Сравнения с NULL нет вовсе** — ни в `where`, ни в списке `in`:
  пустота проверяется только `is null` и `is not null`.
- **Значения в тексте руками не проверяются на смысл**: число знаков —
  да, а что образец `like` или имя в кавычках верны — нет.
- **Обратная черта в тексте руками не экранирует кавычку.** Для MySQL
  с `'it\'s'` разбор найдёт незакрытую кавычку и откажет; кавычку
  удваивают.
- **`upsert` у SQL Tarantool нет.** Для спейса — `box.space.x:upsert`
  либо модель [`tnt-model`](https://github.com/tnt-skein/tnt-model).
- **`returning` — только PostgreSQL.** У MySQL последний ключ и число
  затронутых строк отдаёт драйвер.
- **Регистр букв у `like`, `prefix` и `contains` — дело сервера.** Пакет
  его не выравнивает.
- **Целое у PostgreSQL — `int8`, а не тип столбца**: столбца построитель
  не знает. Индекс сравнение берёт, но в выражении целое ведёт себя как
  целый литерал SQL. Деление двух целых — целое: `sql.raw('? / ?', 7, 2)`
  даёт `3`, а не `3.5`. Функция с аргументом `integer` его не примет:
  `repeat('ab', $1::int8)` — «function repeat(unknown, bigint) does not
  exist». Нужный тип пишут в тексте руками поверх знака — `?::int`
  и `?::numeric` становятся `$1::int8::int` и `$1::int8::numeric`.
